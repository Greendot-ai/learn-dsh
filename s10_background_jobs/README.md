# 10 · 让工作继续，也让它能停下来

上一章：[子代理](../s09_subagents/README.md) · [课程目录](../README.md) · 下一章：[组合 Harness](../s11_harness/README.md)

本章目标：让任务在启动调用返回后继续运行，并能按 ID 查询、等待和取消。

## 要解决的问题

工具一直等待长任务完成时，Agent 循环也无法继续推进。若只启动一个 Promise 后立即返回，又容易丢失状态和异常。本章为后台任务分配 ID，并集中管理状态、取消信号与结束时间。

## 核心机制

[Jobs](../lib/jobs.ts) 为每个任务保存 ID、状态、AbortController 和表示实际结束的 Promise。

```text
start → running → done
                → failed
cancel / dispose → 发出取消 → 等工作退出 → cancelled
```

| 方法 | 行为 |
|---|---|
| `start` | 启动工作并立即返回任务 ID |
| `status` | 返回当前状态的快照 |
| `wait` | 等待任务结束并返回最终状态 |
| `cancel` | 发出取消信号，等待任务退出后返回状态 |
| `dispose` | 拒绝新任务，取消现有任务，并等待全部退出 |

普通异常会被收集到 `failed` 状态，调用者可以查询错误结果。

取消需要任务主动配合。示例计时器使用支持 `AbortSignal` 的 `node:timers/promises`，收到信号后中断等待，Jobs 才记录 `cancelled`。如果任务忽略信号且一直不结束，清理也会一直等待；进程终止等更强的中断机制不在本章范围内。

## 运行

```sh
npm run lesson -- 10
```

预期一个任务为 `done`，另一个为 `cancelled`。演示不需要等满 60 秒；取消会提前中断长计时器。

## 动手练习

1. 创建一个直接抛错的任务，检查状态为 failed 且包含可读错误。
2. 在任务主体的 `finally` 中释放资源，确认 `cancel()` 返回之前已经完成释放。
3. 调用 `dispose()` 后再 `start()`，确认入口拒绝新任务。

完成标准：任务不因最初的工具调用返回而丢失，所有异常可查询，卸载时没有遗留工作。

## 与真实 dsh 的对应

官方把任务能力、执行提供方和模型工具拆到 jobs 相关包。这里全部保存在内存，进程重启后不能恢复，也没有持久队列和并发配额。官方入口见[对应表](../docs/official-map.md)。
